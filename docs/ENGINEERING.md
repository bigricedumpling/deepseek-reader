# 工程原则

## 保留当前技术栈

Vue 3 与 Vite 适合这个 Web 阅读界面，Node.js 文件服务适合插件内运行，SQLite 适合本地索引、事务和元数据。当前没有证据要求更换框架或把正文搬进数据库。

Milkdown 与 Markdown 原文之间存在格式表达差异。保留不能无损往返时的源码保护；不可把所有 Markdown 强制规范化作为默认保存策略。

## 渐进类型化

从 `src/contracts/reader.ts` 开始，先为新增接口的输入输出定义类型，再逐步拆分文档状态、插件连接与存储服务。`npm run typecheck` 当前覆盖契约与 `src/services` 的实际 HTTP/历史版本边界（含返回结构检查与错误类型），不代表整个 Vue/JS 工程已通过完整类型检查。

类型不能替代服务端路径、权限和版本检查，也不能代替真实安装验证。无需为了 TypeScript 一次重写编辑器与全部旧组件。

## 服务生命周期

服务记录按数据目录保存身份与端口。同一库重启复用地址，保持浏览器站点数据；遇到端口冲突明确报错，不跳到另一份空库。已接入旧服务时保留连接，原服务离线不会自动迁移数据。

新构建不加载文件服务，避免仅打包页面就创建真实知识库的元数据。生命周期测试使用临时目录与实际 HTTP 服务，区别于插件工具的模拟请求测试。

## 发布隔离

构建与打包使用独立测试数据。发布源码和插件包不应携带知识库、用户凭据或部署专用配置；升级程序不应覆盖用户内容。公开路由与权限兼容测试保留。

正式发布需要安装包级验收：干净 profile 安装、重启、升级、卸载后数据保留、两工作区并行使用。CI 通过不等于这些人工宿主验收已经完成。

## 已抽离的业务边界

工作区浏览记录、历史请求、差异展示、Markdown 原格式阅读、PDF 阅读、PDF 目录提取、回收站、备份与恢复副本进程分别维护。大型旧组件尚未整体重写；按可独立测试的业务逐步拆分。

PDF.js 在首次打开 PDF 时加载，随包携带 worker、CMap 和标准字体。H5 使用仅允许脚本的 sandbox iframe，不授予同源权限。渲染 Markdown 经过 HTML 清理，公式仅保留几何样式。
